Core pipeline — data flow & module responsibilities
① Input
File path or byte stream. Supports stdin piping, file paths, and raw bytes API. Never loads entire file upfront.
streamingpathlib.PathBinaryIO
↓
② File analyzer
Reads first 8KB only. Detects MIME type via magic bytes (python-magic). Classifies as: text / json / binary / archive / already-compressed.
analysis.detector
③ Entropy estimator
Shannon entropy on sample. High entropy (≥7.5 bits/byte) → already compressed or random, skip. Low entropy → compressible.
analysis.entropy
④ Profiler
Repetition score (most-common byte / total). Semantic detection (UTF-8 valid + word ratio). Produces FileProfile dataclass.
analysis.profiler
↓ FileProfile
⑤ Strategy selector
Consumes FileProfile. Runs registered scoring rules. Returns ordered list of (backend, params). First backend that succeeds is used; rest are fallbacks.
strategy.selectorstrategy.rulesstrategy.plugins
↓ PipelineConfig
⑥ Semantic backend
Tokenize → train dict → bit-pack → optional secondary pass (brotli on token stream). Returns CompressedChunk.
semantic_backend
⑥ Traditional backend
zlib / brotli / lzma / gzip. Each implements AbstractBackend: compress(stream) → stream, decompress(stream) → stream.
backends/
⑥ Hybrid pipeline
Semantic encoding first, then brotli on the token-bit stream. Only worth doing when semantic ratio > 1.3× alone. Benchmarked, not assumed.
pipeline.engine
↓ compressed bytes + method_id
⑦ Crypto layer (optional)
AES-256-GCM. PBKDF2-SHA256 key derivation (200k rounds). Salt + nonce generated fresh per file. Authenticated encryption — no separate HMAC needed. Pass-through if no key provided.
crypto.aes_gcm
⑧ Integrity layer
CRC32 of plaintext before compression. Stored in header. Verified on decompress. Detects silent corruption independent of AES-GCM tag (which only covers ciphertext).
crypto.integrity
↓
⑨ Container packager — formats.writer
Writes .amap file: magic + version + flags byte + all header metadata + compressed (+ optionally encrypted) payload. Supports streaming write — never buffers full output in memory.
formats.writerformats.header
↓
⑩ Output — .amap file or stdout stream

Plugin architecture: Each backend registers with @register_backend("name"). Strategy rules are pure functions score(profile: FileProfile) → float. The selector picks the highest-scoring registered backend above a minimum threshold. Users can inject custom backends without touching core code.
Semantic compression engine — design notes
Tokenizer (current → improve)
Current: whitespace split + regex. Keep this — it's correct. Add: phrase detection for 2–3 word sequences exceeding frequency threshold. Phrases get their own token IDs.
semantic.tokenizer
Dictionary training
Current dict limit: 4096 (12 bits). This is correct. Improvement: sort by frequency × length, not just frequency. Longer common phrases save more bits per occurrence.
semantic.dictionary
Bit packing (current → keep)
Current BitWriter / BitReader implementation is solid. Improvement: variable-width encoding — most-common tokens use fewer bits (proto-Huffman). Realistic 5–15% gain on dense text.
semantic.bitpacking
OOV handling (current → fix)
Current: OOV sentinel + raw bytes. This bloats output for technical text (code, URLs, IDs). Fix: OOV escape + raw UTF-8 length prefix + bytes. Encode OOV as: [OOV_ID][len:u16][raw_bytes]. Avoids wasting bits on tokens that appear once.
Case encoding (current → keep)
Current 2-bit case encoding (lower / title / upper) is efficient and correct. Small improvement: add a MIXED case flag + store original for rare cases where word has internal caps (camelCase, acronyms with mixed case).
What NOT to build (semantic overengineering)
Do not implement: LLM-based semantic compression, neural embeddings, context-dependent dictionaries that require model inference, or "meaning-preserving compression." These are either computationally prohibitive or not lossless. AlphaMap must be 100% lossless. The compression wins come from statistical patterns, not semantic understanding. Keep the "semantic" label but think of it as "token-frequency encoding."

Proposed .amap container format (v2)
MAGIC 4B
VER 1B
FLAGS 2B
SALT 16B
NONCE 12B
HDR_LEN 4B
HEADER variable
PAYLOAD variable
TAG 16B
Flags byte → expand to 2 bytes
bit 0: embedded dict
bit 1: zlib fallback (→ rename to "method" field)
bit 2: encrypted
bit 3: streaming chunks
bit 4: crc32 present
bits 5–15: reserved
Header JSON → MessagePack
Current: JSON embedded header (human-readable but wasteful). Proposal: MessagePack binary serialization. Smaller, faster to parse. Keep JSON as debug option behind a flag.
Header fields (v2)
method: u8 (enum)
original_size: u64
crc32: u32
dict: optional bytes
created_at: u32 unix
filename: optional str
chunk_size: u32
Extension: .amap → rename from .am11
Magic bytes: AMAP (4 bytes). Version bump in byte 5 allows forward incompatibility detection. Tools should refuse to decompress future versions with a clear error, not silently fail. Maintain a CHANGELOG of format version changes.
CLI design — professional command surface
$ alphamap compress input.txt output.amap # auto-strategy
$ alphamap compress input.txt --strategy semantic # force backend
$ alphamap compress input.txt -k password # + AES-GCM
$ alphamap compress input.txt --no-embed-dict -d dict.json
$ alphamap decompress file.amap -o recovered.txt
$ alphamap decompress file.amap -k password
$ alphamap analyze input.txt # file profile report
$ alphamap analyze input.txt --json # machine-readable
$ alphamap inspect archive.amap # show header + meta
$ alphamap inspect archive.amap --json
$ alphamap train corpus.txt -o dict.json --size 8192
$ alphamap benchmark # built-in datasets
$ alphamap benchmark myfile.txt --vs gzip,brotli,lzma
$ alphamap benchmark --output report.json
Implementation note: use Click (not argparse) for the CLI layer. Click's decorator style, automatic help generation, and subcommand nesting are cleaner than argparse for a tool of this size. Keep one cli/commands/ file per subcommand.

Engineering advice — what to do and what to skip
Build these
  • Benchmark first, optimize second. Let data drive decisions about which strategies actually win.
  • AbstractBackend ABC early — makes adding lzma/brotli backends trivially easy.
  • Pure-function strategy rules (score(profile) → float). Stateless = testable.
  • FileProfile dataclass — a single typed container for analysis output keeps the pipeline clean.
  • CRC32 integrity check independent of AES-GCM (detects corruption on unencrypted files).
  • Format versioning with hard rejection of unknown versions (fail loud, not silent).
  • Click-based CLI — decorator style is far cleaner than argparse for subcommands.
  • Streaming I/O from the start — refactoring later is painful.
Skip these
  • LLM/neural semantic compression — not lossless, not realistic for this project.
  • Custom Huffman tree in Python — brotli already does this better in C.
  • Async I/O — adds complexity, no throughput benefit for single-file compression.
  • GUI — out of scope for a systems compression tool at this stage.
  • zstd backend — great algorithm, but adds a C dependency; add in v3 only.
  • Dictionary federation / cloud sync — overengineered for v1.
  • ML-based strategy selection — rule-based scoring + benchmarks is sufficient and debuggable.
  • MessagePack header before v0.2 — JSON header is readable and fine for now.
Realistic compression expectation
AlphaMap's semantic backend will beat gzip/brotli on highly repetitive text with a small vocabulary (legal docs, logs with repeated fields, config files). It will lose on source code, JSON with varied keys, and any text with many OOV tokens. This is fine — that's why you have the strategy selector and fallbacks. The goal is not "always better than brotli" but "never worse than the best of gzip/brotli/lzma" with sometimes significant wins on target workloads. The benchmark system will prove this with real data.
